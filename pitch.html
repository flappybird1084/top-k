It evolves the model, not the kernels.

An agent writes an adapter for your PyTorch training script, then a staged evolutionary search proposes architecture and optimizer changes, trains each one for the same wall-clock budget on one GPU, and ranks them by held-out validation loss. Everything an agent could cheat — data, loss, validation batches, eval code, seeds, the budget, the parameter cap — is owned by the harness. No model ever grades its own output. We started this as a Triton kernel optimizer; the profile numbers below are why the architecture became the main mode and kernels became the second one.

01The measurement that redirected the project

We built the kernel optimizer first, ran it, and profiled honestly. Two results together cap the whole category: the addressable share of a training step is small, and the thing occupying it is already a Triton-writing compiler running near the bandwidth ceiling. The architecture has no such cap.

Why this reframed the product. A perfect kernel optimizer on the second row buys you a fraction of 23%. Changing what the model computes — the norm placement, the MLP shape, the optimizer, the schedule — moves loss-per-second with no equivalent ceiling. So the search moved up a level, and the objective changed from step time to held-out loss under a fixed budget.

02What the search actually evolves

A candidate is one self-contained Python file exposing build_model(), make_optimizer(model), and optionally lr_schedule(step) and TRAIN_HINTS. That is the entire surface. Candidates are told to subclass or patch the repo's own model classes rather than rebuild them — a rebuild silently drops positional encodings, norm placement and init, and reliably scores worse.
Architecture
2 generations × 8 candidates · 60 s each
Redesign the model and optimizer freely, inside the parameter cap and call-compatible with the repo's loss.
Hyperparameters
1 generation × 8 candidates · 120 s each
Architecture frozen to the parent and verified by parameter-shape fingerprint. Only the optimizer, schedule and clipping may move.
Finals
top 2 · 300 s each
The survivors get a longer budget against a baseline retrained at that same budget.
Signal
8 held-out val batches
Accepted only if val loss beats the budget-matched baseline by more than 0.3% — enough to clear the ±1-step noise a wall-clock budget introduces.
The baseline is trained, not remembered. The harness trains the unmodified repo model at every budget the schedule uses, so a 60-second candidate is only ever compared against a 60-second baseline. That is the whole reason a wall-clock objective is safe to optimize against: a candidate that is fast but converges badly, or elegant but slow, is scored by the same number either way. The DEV schedule above is about 42 minutes of GPU time end to end.

03The loop, and what it costs to run

A planner names specific strategies in plain language; parallel subagents implement exactly what they were named; the harness evaluates; a curator distils each generation into lessons injected into the next generation's prompts. Failed-to-author strategies are marked untested, so the planner can re-propose the idea in a simpler form instead of learning the wrong lesson from it.

State and observability

  • archive.sqlite is the only state the loop reads. W&B and Weave are a one-way mirror, written after the archive commits, and never read back.
  • Every LLM call, repair and candidate lifecycle is traced in Weave; per-candidate W&B runs carry per-step train loss, the matched baseline, parameter count, phase and acceptance.
  • Harness failures are tagged [infra] so the curator can't diagnose a SQLite threading bug as a bad architecture idea. It did exactly that before the tag existed.
  • A sandbox that dies mid-run can't take accepted code with it — candidate and recipe sources sync back on every mid-run checkpoint.

Measured cost and latency

  • Whole DEV run: $2.50 – $4.20. One generation ≈ $2 – $2.50. A planner call is $0.15 – $0.40; a candidate including repairs is $0.70 – $1.50.
  • Session total across 5 jobs, 2 target repos and ~9 remote GPU runs: ~$28 of the $100 credit.
  • Completions run 60 – 120 s for a full file at 3 – 6k output tokens, so generations are LLM-bound. The GPU is the stopwatch, not the load — which is exactly why candidates are evaluated the moment their authoring finishes rather than in lockstep at the end of a generation.
  • Runs locally or dispatched to a molab notebook's GPU: paste the notebook's pairing prompt into the web form and jobs are uploaded, streamed and synced back.

04Kernel mode, kept as the second option

The original mode still ships, and it is where the verified end-to-end result lives. Same evolutionary loop, different objective: agents write Triton kernels for the hot ops, and the objective is training step time instead of loss. Correctness is a constraint enforced by four deterministic gates, cheapest first. Pick a real candidate from our runs and watch where it dies.

The one that got through

A row-parallel Triton RMSNorm on nanochat: 8.95 ms → 8.58 ms, −4.1% against per-op torch.compile incumbents and −1.7% against eager, with gradients verified.

It won on the compiler's weak flank, not by out-tuning it. A hand-fused forward+backward pair replaced inductor's autograd-generated backward. The −4.1% step win exceeds the op's 2.3% GPU-time share because an 8 ms step is launch-bound, so deleting launches saves more wall time than it saves GPU time.

Where kernel wins actually live

  • Boundary-moving fusions the compiler never performs. Fusing the head matmul into the loss avoids materialising ~3.2 GB of bf16 logits per step at 32k tokens × 50,304 vocab. Our adapter agent routed modern-lm through that boundary — 5.38% of step versus 1.56% for bare cross-entropy — but the funded search on it was stopped at calibration.
  • Backward passes. Every SwiGLU failure we logged was a gradient bug, and every accepted win was a backward.
  • Launch-overhead regimes. On the 8 ms step, per-op compile wrappers' guard overhead across 73 norm calls made the compiled incumbent no faster than eager.

05What's verified, and what isn't

You are judging this with the same instincts we used to reject our own gen-2 kernel, so here is the honest split.

Verified end to end

  • One agent-written kernel accepted through all four gates on a stranger repo, outputs and gradients checked, step time improved against a re-measured compiled incumbent.
  • Two correct rejections: a flattering microbenchmark win refused because its in-model delta sat inside the calibrated noise margin, and both planted cheating kernels rejected at every single startup.
  • Adapter self-assembly on a 481M-param repo we hadn't seen: op routing matched 73 norms and 24 SwiGLUs behaviourally, never by class name.

Not yet, and known limits

  • No accepted kernel on the 481M repo at DEV search scale; the funded RUN search was stopped by us at calibration.
  • Finalist and parent selection still ranks raw losses across phases with different budgets without normalising them. The UI deliberately groups plotted comparisons by equal budget; the engine ranking is the thing to fix next.
  • The hyperparameter-phase guard checks parameter names and shapes, not full semantic equivalence. A candidate could in principle change behaviour while keeping the fingerprint.
  • Wall-clock budgets introduce ±1-step noise in val loss. The 0.3% margin absorbs it; it does not eliminate it.
